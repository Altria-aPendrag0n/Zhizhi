# 客户端登录与服务端安全同步设计调研

> 背景：知枝已完成服务端 Phase 1（`server/`：验证码登录 / access+refresh / /api/me，见 [21-auth-server](../code-wiki/21-auth-server.md)）。本文调研**客户端如何接入登录**、**服务端与客户端如何安全地保持状态同步（令牌续期 / Key 下发 / 套餐额度 / 配置更新）**，以及**开发期本地部署与发布期地址配置**的落地方式。
> 结论先行：桌面端登录 = 验证码换取短时 access_token（仅内存）+ 不透明 refresh_token（OS 钥匙串，轮换续期）+ 官方 Key 直入钥匙串；安全同步 = HTTPS + 令牌轮换 + 受控凭据边界 + `/api/me` 按需轮询；地址 = 设置项可配置（默认开发 `http://127.0.0.1:8787`，发布 `https://api.zhizhi.app`），并同步放宽 Tauri CSP `connect-src`。

## 一、现状盘点（已具备 / 缺口）

| 项 | 现状 | 缺口 |
|---|---|---|
| 服务端 API | `POST /api/auth/send-code \| login \| refresh \| logout`、`GET /api/me` 全部就绪（30 例测试） | 无 |
| 登录 UI | [OfficialModelPage.vue](../study-thread/src/views/OfficialModelPage.vue) 骨架：登录表单 + 套餐卡片，交互统一"未上线"提示 | 接真实接口 |
| Provider 抽象 | [provider-factory.ts](../study-thread/src/api/provider-factory.ts)：`openai-compat` 适配器可直接对接官方网关 | 官方预设未接线 |
| 凭据存储 | [settings.ts](../study-thread/src/stores/settings.ts) 把 apiKey/baseUrl **明文存 localStorage**（`study-thread-settings`） | 官方 Key/token 必须迁 OS 钥匙串 |
| 安全配置 | [tauri.conf.json](../study-thread/src-tauri/tauri.conf.json) 已有 CSP（`connect-src` 白名单各家 LLM 域名）与 updater（minisign 签名） | CSP 缺官方 API 域名 |
| Rust 插件 | opener / dialog / updater / process | 缺 keyring 类凭据存储插件 |

> 关键认知：**localStorage 不加密地落在用户数据目录，同用户任意进程可读**。对官方 Key（= 钱）与 refresh_token（= 会话永续）而言这是不可接受的风险。桌面端敏感凭据必须走系统钥匙串（Windows Credential Manager / macOS Keychain / Linux Secret Service）。

## 二、客户端登录设计

### 2.1 登录流程（复用已实现的服务端接口）

```
OfficialModelPage（登录表单）
  1. 输入账号（邮箱/手机号）→ POST /api/auth/send-code
     → 60s 冷却倒计时（响应 cooldown_seconds）
  2. 输入 6 位验证码 → POST /api/auth/login
     → 响应：access_token(2h) + refresh_token(30d, 仅响应出现) + user + api_key(仅首登出现)
  3. 凭据落位：
     access_token  → 仅内存（Pinia auth store，重启即丢）
     refresh_token → OS 钥匙串（keyring）
     api_key       → OS 钥匙串（明文只在登录响应出现一次）
  4. 自动启用官方 Provider：openai-compat + 官方 baseUrl + keyring 中的 api_key
     （复用 createProvider，LLM 调用链路零改动）
  5. 拉取 /api/me → 展示账号/套餐/剩余额度
```

### 2.2 凭据存储：tauri-plugin-keyring

选用 **tauri-plugin-keyring**（跨平台，MIT 双许可）：

| 平台 | 底层 |
|---|---|
| Windows | Credential Manager（可用硬件安全） |
| macOS/iOS | Keychain Services（Secure Enclave） |
| Linux | D-Bus Secret Service（GNOME Keyring / KWallet），可选 kernel keyutils |
| Android | Android Keystore |

接入三步（与既有插件模式一致）：

```toml
# src-tauri/Cargo.toml
tauri-plugin-keyring = "0.2.0"
```
```bash
npm add tauri-plugin-keyring-api
```
```json
// src-tauri/capabilities/default.json
"permissions": [
  "core:default", "process:default", "opener:default", "dialog:default", "updater:default",
  "keyring:allow-initialize-keyring", "keyring:allow-set-password",
  "keyring:allow-get-password", "keyring:allow-delete-password",
  "keyring:allow-has-password", "keyring:allow-set-secret", "keyring:allow-get-secret",
  "keyring:allow-delete-secret", "keyring:allow-has-secret"
]
```

JS API（渲染进程直接可用）：`initializeKeyring(service)` → `setPassword/getPassword/deletePassword/hasPassword`（字符串）+ `setSecret/getSecret`（字节）。条目设计：

| 条目（username） | 内容 | 说明 |
|---|---|---|
| `zhizhi.refresh_token` | refresh_token 字符串 | 会话永续凭据，仅 refresh 时经内存过手 |
| `zhizhi.api_key` | `sk-zhizhi-*` 字符串 | 官方 Key，仅在构造 Provider 时读出注入内存 |

> service 名统一 `com.study-thread.app`（与应用 identifier 一致），每个 service 独立凭据存储域。

### 2.3 auth store（Pinia，`stores/auth.ts`）

```
state:  status: 'anonymous' | 'authenticating' | 'authenticated'
        user: { id, identifier, plan_id, plan_expires_at, quota_tokens } | null
        accessToken: string (仅内存)      // 进程内有效
actions:
  sendCode(identifier)                     → POST send-code（返回 cooldown_seconds）
  login(identifier, code, deviceId?)       → POST login
        → setPassword('zhizhi.refresh_token', refresh_token)
        → setPassword('zhizhi.api_key', api_key)（仅首登）
        → accessToken = access_token；user = ...
  restore()                                → 启动时 hasPassword('zhizhi.refresh_token')
        → 有则 silentRefresh() 恢复会话
  silentRefresh()                          → POST refresh（轮换）
        → 新 refresh_token 写回钥匙串；accessToken 更新
  fetchMe()                                → GET /me 更新 plan/quota（见 §3.4）
  logout()                                 → POST logout + 删钥匙串两项 + 清内存
        → 回 anonymous，切回 BYOK/未登录态
```

### 2.4 API 客户端（`api/zhizhi-api.ts`）与 401 自动续期

核心难点：**access_token 2h 过期后要静默续期，且并发 401 只触发一次 refresh**。

```
request(path, options):
  1. 注入 Authorization: Bearer accessToken
  2. 发请求
  3. 若 401 且非 /auth/refresh 自身：
       - single-flight：全局一个 refreshPromise（并发请求共享）
       - 等待 refresh 完成 → 用新 accessToken 重放一次原请求
       - refresh 失败/refresh 也 401 → 清凭据 → 通知 UI 回登录页
  4. 网络错误 / 5xx：抛统一 ApiError（可区分 429/401/网络/超时）
```

要点：
- **refresh_token 永不进 localStorage**，也不进内存之外的任何持久层；refresh 调用时临时从钥匙串读出，完成后立即丢弃。
- baseUrl 取设置项 `officialApiBaseUrl`（见 §四）。
- 超时与重试：send-code/login 这类交互接口设短超时；refresh 失败不自动重试（防风暴），由下次 401 或启动时再触发。
- 离线策略：网络不可用时不破坏本地数据（会话文件照常可写），仅提示"官方服务不可达"。

### 2.5 登录 UI 状态机（OfficialModelPage）

| 状态 | UI |
|---|---|
| anonymous | 登录表单（账号 + 验证码 + 获取验证码倒计时）+ 套餐卡片 |
| authenticating | 按钮 loading + 禁用 |
| authenticated | 显示账号/套餐/剩余额度 + 用量说明 + 登出按钮 |
| error | toast 展示 401（验证码错误）/ 429（限频，带冷却秒数）/ 网络错误 |

> 登录成功后"自动配置"的可见性：可仿照现有 `handleNotReady` 位置放一个"已连接"状态卡，说明"官方 API 已启用，无需手动配置 Key"。

## 三、服务端 ↔ 客户端安全同步（"安全更新"）

### 3.1 传输安全

| 环境 | 地址 | 安全要求 |
|---|---|---|
| 开发 | `http://127.0.0.1:8787` | 仅回环地址；服务端绑定 127.0.0.1 而非 0.0.0.0，避免局域网嗅探；`VERIFY_CODE=log` 取码 |
| 生产 | `https://api.zhizhi.app` | TLS 1.2+，系统信任链验证（fetch 默认）；**绝不可用 HTTP 走公网** |

- 服务端 `cors()` 目前全放行：**生产必须收紧**为白名单（如 `tauri://localhost`、`http://tauri.localhost`、官方客户端 origin 列表）。
- 令牌只走 `Authorization` 头，绝不进 URL query / 日志。

### 3.2 令牌生命周期（服务端已实现，客户端配合）

| 令牌 | 生命周期 | 客户端职责 |
|---|---|---|
| access_token（JWT HS256） | 2h | 仅内存；过期靠 401 → silentRefresh |
| refresh_token（不透明，库存 sha256） | 30d，**每次使用即轮换** | 钥匙串持久化；单线程消费（single-flight） |
| api_key（`sk-zhizhi-*`，库存 hash） | 长期，可吊销 | 登录响应明文仅一次 → 直入钥匙串 |

- **轮换 = 重放检测**：旧 refresh 一旦被再次使用即 401（服务端已实现"旧记录作废"），客户端应把该 401 视为"凭据被盗或本地损坏"→ 强制重新登录。
- 建议后续增强（可选）：refresh 增加 `last_used_at` 空闲超时（如 7 天未用即失效），参考 OAuth 桌面实践中的 idle-expiry 做法。

### 3.3 凭据边界（威胁模型核心）

```
┌─────────────────────────────────────────────────────────┐
│ 渲染进程（Vue）                                            │
│   access_token：仅内存变量（不落盘）                        │
│   api_key：仅在构造 Provider 时短暂存在于 JS 内存            │
│   refresh_token：全程不经 JS 持久层                        │
└───────────────┬─────────────────────────────────────────┘
                │ invoke（受控 IPC）
┌───────────────▼─────────────────────────────────────────┐
│ Rust 后端                                                   │
│   keyring（OS 钥匙串）：refresh_token / api_key            │
│   → 渲染进程只能通过白名单权限的 keyring 命令读写            │
└─────────────────────────────────────────────────────────┘
```

- **明确禁止**：把 refresh_token / api_key 写入 `localStorage` 或任何 JSON 设置文件（即使"加密"也不如钥匙串——自研加密密钥还得存本地，等于没有）。
- 现有 `study-thread-settings` 里如果曾经存过官方 Key，接入时做一次迁移清理（发现钥匙串条目后删除 localStorage 副本）。

### 3.4 状态同步：套餐 / 额度 / 配置更新

"安全更新"除令牌外，还指**服务端可靠地把用户状态与配置同步到客户端**：

| 同步项 | 拉取方式 | 触发时机 |
|---|---|---|
| 会话续期 | `POST /auth/refresh`（轮换） | 启动 restore、任意接口 401 |
| 用户/套餐/额度 | `GET /api/me` | 登录成功、应用启动、购买/开通后、设置页打开时 |
| 用量（Phase 2） | `GET /api/usage` | 按需 + 本地缓存；MVP 不必实时 |
| 服务端配置（模型列表/feature 开关/最低客户端版本） | `GET /api/config`（Phase 2 新增，返回 `{version, models[], features{}}`） | 启动 + 定时（如每小时），本地按 version 缓存，服务端变更仅推送增量 |

- MVP 用**轮询/按需拉取**即可，不需要 WebSocket/SSE（桌面应用非实时场景，省去长连接与重连复杂度）。
- 每次 `/api/me` 或 `/api/config` 响应都更新本地 auth store 与设置，保证"服务端改了什么，客户端下次启动即生效"。

### 3.5 Tauri CSP 更新（关键工程点）

当前 [tauri.conf.json](../study-thread/src-tauri/tauri.conf.json) 的 CSP 把 `connect-src` 写死为各家 LLM 域名列表。官方 API 域名必须加入，否则 WebView fetch 被 CSP 拦截：

```jsonc
// 开发（tauri dev）：
"csp": "default-src 'self'; connect-src 'self' http://127.0.0.1:8787 https://...; ..."
// 生产（tauri build）：
"csp": "default-src 'self'; connect-src 'self' https: https://...; ..."
```

**取舍（重要）**：CSP 是编译期写死的，而官方地址要"运行时可在设置页修改"。若 CSP 只允许固定域名，用户改了地址即被拦。两种解法：

1. **生产 CSP 放行 `https:` 前缀**（推荐）：任何 HTTPS 站点都可连，但请求仍受 CORS 约束 + 系统证书链验证，对桌面应用风险可控（业界常见做法）。代码层再加一道防线：仅当目标 host 是官方域名或用户在设置中显式确认过的地址时才注入令牌。
2. **构建时注入地址**：`VITE_OFFICIAL_API_URL` 在 `tauri build` 时同时写入 CSP 与默认设置。严格但改地址需重新打包（不利于自托管/灰度）。

> 建议：**默认值构建时注入（开发 `http://127.0.0.1:8787` / 发布 `https://api.zhizhi.app`），CSP 生产用 `https:` 放行，设置页提供"官方服务地址"高级项**。二者可同时成立：默认值省心，设置项兜底。

### 3.6 与"应用二进制更新"的边界

应用自身的自动更新走已有 **tauri-plugin-updater**（GitHub Releases + minisign 公钥验签，见 tauri.conf.json），与本文的"数据/会话同步"是两个独立通道：
- 二进制更新：验签 + 版本门控，防篡改分发；
- 数据同步：HTTPS + 令牌轮换 + 钥匙串，防凭据泄露。
两者互不替代。

## 四、开发本地部署与发布地址配置

### 4.1 开发期

```
终端 1：cd server && npm run db:migrate && VERIFY_CODE=log JWT_SECRET=dev-secret npm run dev
        → 监听 http://127.0.0.1:8787（验证码输出到日志，冒烟取码）
终端 2：cd study-thread && npm run tauri dev
        → 客户端设置「官方服务地址」= http://127.0.0.1:8787（开发默认值）
```

- 服务端 `.env.example` 已含 `PORT/JWT_SECRET/DB_PATH/VERIFY_CODE`；开发用独立 DB 文件（如 `DB_PATH=./data/dev.db`），避免污染。
- 前端测试（vitest）里 mock `api/zhizhi-api.ts`，不依赖真实服务端。

### 4.2 发布期

- 设置项 `officialApiBaseUrl`（settings store 新增字段）：
  - 默认值 = 构建环境注入：`import.meta.env.VITE_OFFICIAL_API_URL`（`.env.production` 里写 `https://api.zhizhi.app`，`.env.development` 里写 `http://127.0.0.1:8787`）；
  - 设置页「官方 API」卡片提供"服务地址"高级输入（默认隐藏，展开显示），保存后即时生效并重测连接。
- **发布前 checklist**：
  1. 服务端 `cors()` 收紧白名单；
  2. CSP `connect-src` 含 `https:`（或注入域名）；
  3. `JWT_SECRET` 用强随机串（`openssl rand -hex 32`），`NODE_ENV=production`；
  4. 服务端部署到 HTTPS 域名，验证证书链；
  5. 打 release 包时 `.env.production` 注入正确地址。

### 4.3 方案对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 构建时硬编码地址 | CSP 可写死、最严格 | 换域名/自托管需重打包 | 作为默认值 |
| 运行时设置项（推荐） | 发布后可改、灰度/自托管友好 | CSP 需放宽 `https:`、需防误配 | **主方案** |
| 自动发现（仅 dev） | 零配置 | 生产不适用 | 仅在 dev 默认 |

## 五、威胁模型与缓解清单

| 威胁 | 缓解 |
|---|---|
| 恶意进程读 localStorage 窃取 Key/token | 凭据全部进 OS 钥匙串；localStorage 只存非敏感偏好 |
| XSS/依赖污染从渲染进程窃取 refresh_token | refresh_token 不经 JS 持久层，仅受控 IPC + 短时内存 |
| access_token 被窃 | 2h 短生命周期，被盗窗口小；泄露后靠轮换/吊销收敛 |
| refresh_token 重放 | 服务端轮换 + 旧 token 立即失效；客户端把重放 401 当"强制重新登录"信号 |
| 中间人（MITM） | 生产仅 HTTPS + 系统证书链验证；开发仅 127.0.0.1 回环 |
| 跨域钓鱼（改 baseUrl 指向恶意站） | 代码层校验：非官方域名注入令牌前需用户显式确认 |
| 服务端数据被拖库 | 验证码/refresh/api_key 全 hash 存储（已实现），无明文凭据 |
| CSP 绕过 | 生产放行 `https:` + CORS 白名单双保险 |

## 六、结论与实施清单（供下一步 todo）

1. **Rust**：接入 `tauri-plugin-keyring`，注册插件 + capabilities 权限；封装 `secure_store` 命令（get/set/delete 两项凭据）或直接用 JS API。
2. **前端**：`stores/auth.ts`（状态机 + 登录/restore/silentRefresh/logout/fetchMe）；`api/zhizhi-api.ts`（baseUrl 注入 + Bearer + 401 single-flight 刷新）；`settings.ts` 增 `officialApiBaseUrl` 字段（默认 `import.meta.env.VITE_OFFICIAL_API_URL`）。
3. **UI**：OfficialModelPage 接真实接口（表单 → 倒计时 → 已登录态 → 登出）；提供"服务地址"高级设置。
4. **Provider 接线**：登录成功 → 官方预设写入 settings（type=openai-compat, baseUrl=official, apiKey=keyring 读出），LLM 链路复用 `createProvider`。
5. **tauri.conf.json**：CSP `connect-src` 加 `https:` 与 `http://127.0.0.1:8787`（dev）。
6. **服务端（配套）**：生产 `cors()` 收紧；可选 refresh 空闲超时；Phase 2 补 `/api/config`、`/api/usage`。
7. **测试**：auth store 单测（mock api + mock keyring）、zhizhi-api 401 并发刷新测试、OfficialModelPage 状态机测试。
