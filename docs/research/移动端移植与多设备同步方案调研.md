# 移动端移植与多设备同步方案调研

> 调研日期：2026-09-04
> 背景：讨论「制作手机版知枝」引出的三个递进问题——①移植难度多大；②是否要先解决同步；③Obsidian 的 GitHub 同步方式 / 借坚果云是否可行。
> 本文结论基于对知枝代码的实际盘点（`src-tauri` 命令、插件依赖、前端 Tauri API 调用点），不是泛泛分析。

---

## TL;DR（三句话结论）

1. **移动端可做，难度中等**：架构意外友好（自定义命令 + 本地文件 + webview 内 ML），粗估 70% 代码可复用，工作量集中在移动 UI 重设计与平台差异适配；建议 Android 先行。
2. **同步不是移动端的前置条件**：桌面多设备同步今天就能用——用户把 Vault 放进坚果云等同步盘文件夹即可，知枝零代码。
3. **移动端同步的正解是内置 WebDAV（预设坚果云）**：一次实现桌面/移动通吃，未来可扩展任何 WebDAV 服务；git 方式借鉴其思想但只做「备份快照」，不做同步主通道。

## 1. 移动端移植可行性

### 1.1 现状盘点（代码证据）

| 层 | 现状 | 移动端影响 |
|----|------|-----------|
| 框架 | Tauri v2（官方支持 iOS/Android） | 同一套 Rust 后端可直接编译，无需换框架 |
| 文件系统 | 全部走 11 个自定义命令（`read_file`/`write_file`/`list_dir`/`extract_pdf_text`/`start_watch` 等，见 `vault.rs`、`pdf.rs`），底层 `std::fs` | ✅ 抽象层极薄，移动沙盒可用；未依赖平台差异大的 `tauri-plugin-fs` |
| JS 插件 | `dialog`（选 Vault/导出）、`opener`、`updater`、`process` | ⚠️ 均需平台分支或替换 |
| Rust 插件 | `keyring`（官方通道凭据）、`notify`（文件监听）、`pdf_oxide` | keyring/notify 无移动端支持；pdf_oxide 纯 Rust 无碍 |
| Embedding | transformers.js（onnxruntime-wasm），模型内置 `public/models` | ⚠️ 移动 webview 可跑（iOS 需 16.4+ 支持 wasm SIMD），老设备内存吃紧、首次索引慢 |
| LLM 调用 | webview fetch https（CSP 已放行） | ✅ 无需改动 |
| UI | 桌面三栏布局、快捷键、鼠标划选摘录 | ❌ 最大的工作量：导航重构、划选摘录改触摸交互 |

### 1.2 难点清单（按工作量排序）

1. **UI 重设计（最大头）**：桌面三栏 → 移动导航；快捷键 → 触控入口；划选摘录的鼠标选区 → 触摸长按选择（核心交互，需重做）；
2. **Vault 位置模型**：桌面任选文件夹 → 移动端仅 App 沙盒（iOS 接 Files.app、Android 走 SAF），选 Vault 逻辑需改；
3. **文件监听失效**：`notify` 在 iOS 无对应 API，`start_watch` 需降级为轮询或 no-op；
4. **凭据存储替换**：`tauri-plugin-keyring` 不支持移动端 → iOS Keychain / Android Keystore 方案；
5. **自动更新关闭**：updater 仅桌面，移动端走应用商店，`updater.ts` 需平台分支；
6. **Embedding 性能与体积**：模型内置使安装包多几十 MB；老设备首次索引慢；
7. **打包链**：Android 简单；**iOS 必须 Mac + Xcode + Apple 开发者账号（$99/年）**。

### 1.3 分阶段建议

- **Phase 1：Android「复习伴侣」瘦身版**——只做复习答题 + 笔记浏览 + 摘录查看。理由：免 Mac、`inotify` 文件监听可用、SAF 选目录，平台障碍少一半；UI 工作量最小，先验证移动需求。
- **Phase 2：全功能移植**（会话、计划、官方通道），视 Phase 1 验证结果决定。

## 2. 同步：要不要先做？四条路线对比

### 2.1 先回答「要不要」

**不需要把自建同步当作移动端的前置条件**。Vault 本身是普通文件夹，「桌面 ↔ 桌面」多设备同步现在就能借用户的网盘实现；移动端与同步可以解耦、分期推进。

### 2.2 参照系：Obsidian 社区的四条路

| 方式 | 服务器成本 | 门槛 | 备注 |
|------|-----------|------|------|
| Vault 放进 iCloud/OneDrive/坚果云同步文件夹 | 零 | 最低 | 最主流，知枝今天即可用 |
| Obsidian Sync（官方付费，E2E 加密） | 高 | 低 | 最佳体验，挂付费体系 |
| obsidian-git 插件（GitHub 方式） | 零 | 高（git + PAT） | 技术型少数用户 |
| Remotely Save 插件（自备 WebDAV/S3） | 零 | 中 | 进阶用户 |

### 2.3 GitHub（git）方式：可借鉴，但只做「备份快照」

知枝 Vault 为纯 Markdown + frontmatter，git 友好度与 Obsidian 相同。但直接当同步主通道有三个坑：

1. **`.study-thread/` 元数据是 git 天敌**：`review-state.json`、会话树等 JSON 由程序高频改写，git 无语义合并能力，两台设备各自复习一天后必然冲突且无法手工解决；
2. **参考资料 PDF 为二进制**：直接入库仓库持续膨胀；排除则移动端缺资料；
3. **门槛与移动端实现**：GitHub 私有仓库 + PAT 对学习者人群太硬核；移动端需 isomorphic-git（慢）或交叉编译 libgit2（痛苦）。

**正确用法**：改造为「**Vault 快照与版本历史**」功能——定期自动 commit 到用户自己的 GitHub 私有仓库，作为防丢失备份 + 回滚手段，强化「数据可携带、可备份」卖点，与同步互补而非互斥。

### 2.4 四条路线总览

| 路线 | 开发成本 | 用户体验 | 适用 |
|------|----------|----------|------|
| A. 用户网盘同步文件夹 | 零（仅文档 + 容错） | 好（桌面端） | 现在就做 |
| B. App 内置 WebDAV（预设坚果云） | 中 | 好（全端） | 移动端 Phase 1 |
| C. git 快照备份 | 小-中 | 技术用户 | 可选加分项 |
| D. 官方 E2E 同步（挂 Zhizhi-Server 账号 + 套餐） | 大 | 最好 | 移动需求验证后，作为付费功能 |

## 3. 借坚果云的具体方案

坚果云的两个关键属性：**国内可直连**（Dropbox/Google Drive 不可达）与**标准 WebDAV 协议**（`https://dav.jianguoyun.com/dav/`）。由此分两种形态：

### 3.1 形态 A：用户装坚果云客户端，Vault 放进同步文件夹（零代码）

- 桌面端多设备同步立刻成立，知枝只读普通文件夹，感知不到坚果云；
- 知枝仅两件事：文档引导；Vault 加载容错（同步盘「半同步」状态下文件可能短暂缺失/占用，补边界处理）；
- **局限**：坚果云移动客户端是「云文件浏览器」模式，不会把第三方文件夹双向同步到手机本地——移动端参与必须靠形态 B。

### 3.2 形态 B：知枝内置 WebDAV 同步引擎（移动端正解）

**用户侧流程**
1. 注册坚果云 → 官网「账户信息 → 安全选项」生成**应用密码**（WebDAV 不用登录密码，独立应用密码，安全）；
2. 知枝设置页「同步」面板：WebDAV 地址（预设坚果云）+ 账号 + 应用密码 + 模式（上传/下载/双向）；
3. 凭据存系统钥匙串（复用官方通道 keyring 机制）。

**引擎设计要点**

| 模块 | 设计 |
|------|------|
| WebDAV 客户端 | Rust 侧 reqwest 实现 `PROPFIND / GET / PUT / MKCOL / DELETE`；流式上传利于大文件 |
| 同步状态机 | 本地扫描（path/mtime/hash）↔ 远端目录树 diff → 上传/下载/删除；墓碑记录防「删除复活」 |
| 触发策略 | 首版仅**手动触发**；同步期间暂停 file watcher（避免边同步边写） |
| 冲突策略 | **只增不删**：冲突版本存为 `xxx.conflict-<设备>-<日期>.md` 副本，绝不静默覆盖；Markdown 为用户手工内容，双版本保留 + 人工合并 |

**针对知枝数据结构的两个关键决策**

1. `references/`（PDF 等大文件）：默认排除或「单向只上传一次」——不可合并、体积大，且坚果云免费版流量有限（上传约 1GB/月，以官网为准），PDF 重度用户需提示；
2. `.study-thread/` 高频 JSON（如 review-state.json）：不同步或「最新写入者赢」；复习调度真相逐步向笔记 frontmatter 的 review 镜像收敛（笔记已含该镜像）——移动端复习后桌面端可由镜像重建调度状态，JSON 冲突不再致命。

**为什么移动端不绕开引擎走别的路**：iOS 沙盒访问第三方 File Provider 很麻烦；Android 依赖 FolderSync 等第三方工具门槛更高。内置 WebDAV 一次实现全端通吃，换预设地址即可支持群晖/Alist/InfiniCloud 等任何 WebDAV 服务。

### 3.3 工程量分解（形态 B）

1. Rust WebDAV 客户端（含限流退避）——中；
2. 同步状态机（diff/上传/下载/墓碑/冲突副本）——中；
3. 设置 UI + 凭据 + 同步状态展示（上次同步、待上传 N、冲突 M）——小；
4. 元数据策略（`.study-thread` 排除 + review 镜像重建）——小-中；
5. 测试（本地 WebDAV server 模拟 + 冲突用例）——中。

## 4. 推荐路线图

| 阶段 | 内容 | 前置条件 |
|------|------|----------|
| 现在 | 文档引导「Vault 放进坚果云同步文件夹」+ 加载容错加固 | 无 |
| 移动 Phase 1 | Android 复习伴侣（复习/笔记浏览）+ WebDAV 同步引擎（预设坚果云，手动触发 + 保守冲突策略） | Phase 1 UI 骨架 |
| 并行可选 | git 快照备份功能（面向技术用户） | 无 |
| 后续 | 元数据 frontmatter 化收敛 → 自动同步 → 官方 E2E 同步挂套餐体系 | 移动需求验证 + 套餐体系成熟 |

## 5. 风险与原则

- **同步是数据破坏型功能**，历史上翻车集中在冲突处理：第一版坚持「手动触发 + 只增不删」，跑稳后再放开自动同步；
- 免费版坚果云流量与请求频率有限制（WebDAV 有每时段请求数限制），引擎需批量、低频设计；
- iOS 端涉及 Mac 打包链与开发者账号成本，务必在 Android 版验证需求后再投入。

## 6. 结论

- 移植：可行且架构友好，Android 瘦身版先行，核心风险在 UI 适配与 iOS 平台差异；
- 同步：先借用户网盘（零代码）覆盖桌面场景，移动端以「内置 WebDAV（预设坚果云）」为正解；
- git：借鉴其「文件即真相 + 版本历史」思想，做成备份快照功能，不做同步主通道；
- 官方同步：留给账号 + 套餐体系成熟后作为付费功能，避免过早背上基础设施负担。
