# 短信与邮箱验证码实现调研

> 背景：知枝将推出账号体系（自有账号 + 验证码登录，见《账号系统与服务器通信设计调研》）。本文调研短信/邮箱验证码的实现方式：服务商选型、接入流程、成本、合规门槛，以及验证码生成/存储/校验的安全最佳实践与常见坑。

---

## 一、结论先行（TL;DR）

1. **验证码本质是一个"一次性短时效凭证"**：生成 → 存储（只存 hash）→ 发送 → 校验（一次性消费）→ 作废。全程 5-10 分钟生命周期，**明文永远不出服务端**。
2. **邮箱验证码是知枝最现实的起步通道**：成本低（免费额度够用）、无企业资质门槛、用户是付费群体必有邮箱；短信在国内有**企业认证 + 签名备案 + 运营商报备**硬门槛，起步成本高。
3. **发送服务只是最后一公里**：安全核心在服务端设计——防爆破（尝试上限）、防重放（一次性消费）、防刷量（发送限频 + 可选图形/滑块挑战）。
4. 邮件服务商推荐 **Resend**（免费额度 + API 友好）；短信推荐**阿里云/腾讯云**（国内主流），但需提前 10-15 个工作日完成资质备案。

---

## 二、验证码全生命周期（通用设计）

```
客户端                      服务端                          通道
  │  1. 请求发送验证码         │                              │
  ├──────────────────────────►│  2. 校验限频（60s 重发/日上限）  │
  │                           │  3. 生成 6 位数字（crypto 安全随机）│
  │                           │  4. 存 hash + TTL(10min)      │
  │                           ├──────────────────────────────►│ 短信API/邮件API
  │                           │                              │ 发送验证码
  │  5. 用户输入验证码         │                              │
  ├──────────────────────────►│  6. 按 identifier 取记录       │
  │                           │  7. 恒定时间比较 → 成功即删除   │
  │                           │  （防重放/防撞码）             │
  │  ◄────────────────────────┤  8. 签发 token（登录成功）      │
```

- 存储载体：**Redis（推荐）或内存/DB**——验证码是"几分钟后就没用"的短时数据，不要写业务主库制造压力。
- Key 设计：`verify:code:{identifier}`（邮箱/手机号），**按"接收方"校验，绝不按"码的值"去查表**（否则两用户撞码会串号）。

## 三、短信验证码（国内）

### 3.1 服务商对比

| 服务商 | 价格 | 免费额度 | 资质门槛 | 备注 |
|---|---|---|---|---|
| [阿里云短信](https://help.aliyun.com/zh/sms/getting-started/get-started-with-sms) | 0.045 元/条起 | 注册送少量 | **个人认证无法签名报备**，需企业认证或短信认证产品 | 验证码限频：1条/分、5条/时、10条/天；70 字拆条计费 |
| [腾讯云短信](https://cloud.tencent.cn/document/product/382/37794) | 约 0.045-0.05 元/条 | — | 签名审核约 2h；**个人无法运营商实名报备** | 报备 7-10 工作日，签名闲置 7天-6月 会被运营商失效 |
| 百度云 SMS | 按量 | — | 需实名 | — |
| 网易云信 | 按量 | — | 需实名 | — |

### 3.2 接入流程与合规门槛（关键！）

一条国内短信 = **【短信签名】+【短信模板】**，发送前必须走完：

1. **实名认证**：个人或企业（阿里/腾讯）。
2. **申请资质**（个人认证的"自用资质"**无法通过运营商签名实名报备**——腾讯明确：个人认证用户需升级企业认证或用「他用资质 + 授权委托书」）。
3. **申请签名**：审核 2 小时至 2 个工作日。
4. **申请模板**：验证码用变量占位，如阿里 `${code}`、腾讯 `{1}`（"您的验证码为${code}，如非本人操作请忽略"）。
5. **运营商实名报备**：**7-15 个工作日**（阿里云官方口径），报备前可少量测试。
6. 获取 AccessKey → 调用 `SendSms`（参数：`phoneNumbers` / `signName` / `templateCode` / `templateParam`）。

> **完整接入时长 10-15 个工作日**（含运营商报备）；生产稳定发送需等报备完成。这是知枝短信通道最大的时间成本。

### 3.3 成本估算

- 验证码 0.045 元/条起，70 字以上拆条。
- 按 1000 用户 × 5 条/月估算 ≈ **225 元/月**；短信验证码适合"高价值操作"（登录、支付）而非高频。

## 四、邮箱验证码（事务性邮件）

### 4.1 服务商对比

| 服务商 | 免费额度 | 起步成本 | 开发者体验 | 备注 |
|---|---|---|---|---|
| [Resend](https://resend.com) | **永久免费 100 封/天**（3000/月） | Pro $20/月 1 万封 | ⭐⭐⭐⭐⭐（8 分钟接入，Node SDK，`{data,error}` 返回） | 作者多为原 Vercel 邮件团队成员；送达率优秀 |
| SendGrid | 2025 年 5 月**取消永久免费层**（仅 60 天试用 100 封/天） | Essentials $19.95/月 | ⭐⭐⭐（SDK 维护模式） | Twilio 生态，量大时可选 |
| Mailgun | **永久免费 100 封/天**（1000/月） | $35/月起 | ⭐⭐⭐⭐ | Webhook/日志能力强 |
| AWS SES | 免费区 62,000 封/月 | $0.10/千封（最便宜） | ⭐⭐（配置复杂） | 需自行做域名验证、IP 预热、退信处理 |
| 国内 SMTP（QQ/163） | 免费 | 0 | ⭐⭐ | 个人开发/测试可用；**送达率不稳、易进垃圾箱**，不建议生产 |

> 参考对比：[Resend vs SendGrid vs SES](https://nextbuild.co/blog/resend-vs-sendgrid-vs-ses-email)、[SendGrid vs Mailgun vs SES 2026](https://www.suprsend.com/post/sendgrid-vs-mailgun-vs-ses)。≤10 万封/月三家价格几乎相同（±$0.05），差异在开发者体验与免费层。Resend 的**永久免费层**对个人项目最友好。

### 4.2 送达率关键（自定义域是必须项）

- 绑定自定义发信域（如 `mail.zhizhi.app`），配置 **SPF / DKIM / DMARC** 三件套，否则大概率进垃圾箱。
- 用服务商默认域（onboarding 域）可达性差；IP 预热、退信/投诉处理也是送达率因素。
- 国内收件方（QQ/163/企业邮箱）对境外服务商（Resend 等）有风控，**需实测送达率**；若国内用户为主，可考虑阿里云邮件推送/腾讯云邮件推送等国内服务。

### 4.3 成本估算

- 起步：Resend 免费层（100 封/天）**0 成本**；1 万封/月也仅 $20。
- 知枝场景（付费用户登录 + 少量通知）几乎可长期免费。

## 五、验证码通用实现与安全要点

### 5.1 生成

- **6 位数字**（`crypto.randomInt(0, 1_000_000)` 补齐），避免字母易混淆问题（0/O、1/l/I——这是图形验证码的教训，数字码天然规避）。
- 若做图形验证码：字符池去掉易混淆字符。
- 不依赖 `Math.random`，用密码学安全随机源。

### 5.2 存储（服务端）

| 要点 | 说明 |
|---|---|
| **不存明文** | 存 SHA-256 hash（防库泄露后撞库）；明文只在"发送那一刻"存在于服务端内存 |
| 载体 | Redis（TTL 原生）> 内存 > 数据库；**不要写业务主库** |
| Key | `verify:code:{identifier}`，按接收方绑定 |
| TTL | **5-10 分钟**（推荐 10 分钟，参考阿里云验证码模板惯例） |

### 5.3 校验（一次性消费，防重放）

- **校验成功立即删除**（"阅后即焚"）——否则同一验证码可被无限重放（经典漏洞，见[Redis 验证码安全](https://blog.csdn.net/qq_45740561/article/details/118733139)）。
- **恒定时间比较**（`timingSafeEqual`），防时序侧信道。
- **错误尝试上限**：连续错 5 次作废该验证码，防暴力枚举。
- **按 identifier 取记录再比对**，禁止"拿输入码去 SELECT"（撞码串号问题）。

### 5.4 防刷量（发送侧限频）

| 维度 | 建议值 |
|---|---|
| 重发间隔 | 60 秒 |
| 单号码日上限 | 5-10 条/天（阿里云平台侧即 10 条/天） |
| IP 维度 | 每 IP 每 10 分钟 ≤ 3-5 次 |
| 全局限流 | 登录接口按 IP/账号限流（令牌桶） |

### 5.5 防机器刷验证码（可选进阶）

- **发送前挑战**：图形验证码（Kaptcha/EasyCaptcha 类，答案只存服务端，`captchaId` 走 HttpOnly Cookie）或行为验证码（滑块，阿里云/腾讯防水墙）。
- 触发策略：仅在检测到异常频率时要求挑战，正常用户无感。
- 注意坑：图形验证码**明文答案绝不能返回前端**（[.NET 实战案例](https://juejin.cn/post/7659884568908480555)）；每次请求重新生成；有效期短（2 分钟）。

## 六、对知枝的建议（分阶段落地）

| 阶段 | 通道 | 做法 |
|---|---|---|
| **开发期** | 日志输出 | `send-code` 接口把验证码打印到服务端日志（`VERIFY_CODE` 环境变量控制），前端开发零依赖联调 |
| **MVP 生产** | **邮箱为主** | 接 Resend（免费层）+ 自定义域 `mail.zhizhi.app` 配 SPF/DKIM/DMARC；标识符支持邮箱；手机号暂提示"暂不支持短信" |
| **国内扩容** | 短信补充 | 需**企业认证**（或他用资质+授权委托书）+ 签名/模板备案 + 运营商报备（预留 10-15 个工作日）；接阿里云/腾讯云 `SendSms` |
| **安全标配** | 服务端 | 一次性消费、错误 5 次作废、60s 重发、日上限、IP 限流、hash 存储、恒定时间比较 |
| **防刷增强** | 图形/滑块 | 出现异常频率时在"获取验证码"前置滑块挑战（阿里云滑块/自绘 canvas），MVP 可后置 |

### 实现位置（对应后端骨架）

- `server/src/services/verify-code.ts`：生成/存储/校验（封装一次性消费 + 限频 + 尝试次数）。
- `server/src/services/notifier.ts`：通道抽象（`send(identifier, code)` 接口），实现 `EmailNotifier`（Resend/SMTP）与 `SmsNotifier`（阿里云/腾讯云，延迟接入），开发期 `LogNotifier`。
- 接口：`POST /api/auth/send-code {identifier, channel}`、`POST /api/auth/login {identifier, code}`。
